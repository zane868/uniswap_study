## 摘要

本协议使用区块链，让不同组织之间无需事先建立信任，就能**发现、选择智能体并与之交互**，为**开放的智能体经济**提供基础。

信任模型可以替换，也可以按风险分层：订购披萨等低风险任务和医疗诊断等高风险任务，需要不同程度的安全保障。开发者可选用基于客户反馈的信誉系统、由质押机制保障的重新执行验证、零知识机器学习（zkML）证明，或可信执行环境（TEE）预言机。

## 动机

模型上下文协议（Model Context Protocol）<!-- 待办：再次确认此处的缩写是否正确。 -->(MCP) 允许服务器列出并提供其能力，包括提示词、资源、工具和补全；Agent2Agent <!-- 待办：再次确认此处的缩写是否正确。 -->(A2A) 则负责智能体身份认证、通过 AgentCard 发布技能、直接通信，以及任务全生命周期的编排。但这些通信协议本身没有解决如何发现智能体、如何判断其是否可信的问题。

要让不同组织的智能体在开放环境中协作，需要一套发现和信任机制。本 ERC 为此定义了三个轻量级注册表，可部署在任意 L2 或主网，每类注册表在每条链上各部署一个实例：

**身份注册表（Identity Registry）**——基于 [ERC-721](https://eips.ethereum.org/EIPS/eip-721) 及 URIStorage 扩展 <!-- 编辑注：URIStorage 在哪里定义？它是 OpenZeppelin 的功能吗？如果是，应在此处提供接口，或另行制定 ERC 将其标准化。 -->的精简链上标识，指向智能体的注册文件，使智能体拥有可迁移、抗审查的身份标识。

**信誉注册表（Reputation Registry）**——用于发布和获取反馈信号的标准接口。评分和聚合可在链上完成，供其他合约调用，也可在链下采用更复杂的算法处理。其他服务可基于这些信号提供智能体评分、审计者网络和保险池。

**验证注册表（Validation Registry）**——提供通用钩子，用于请求独立验证并记录结果。验证方式包括质押者重新执行任务、zkML 验证器、TEE 预言机，以及受信任的裁定方检查。

支付机制独立于本协议，不在本标准范围内。文中的示例说明了 **x402 支付** <!-- 编辑注：这是 Coinbase 的东西，对吗？如果它不是本标准必需的内容，能否省略？ -->如何为反馈补充信息。

## 规范

本文中的关键词“必须（MUST）”“不得（MUST NOT）”“必需（REQUIRED）”“必须（SHALL）”“不得（SHALL NOT）”“应当（SHOULD）”“不应当（SHOULD NOT）”“推荐（RECOMMENDED）”“不推荐（NOT RECOMMENDED）”“可以（MAY）”和“可选（OPTIONAL）”，应按照 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 和 [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) 的说明解释。

### 身份注册表

身份注册表使用 ERC-721 及 URIStorage 扩展来注册智能体，因此，**兼容 NFT 的应用可以直接浏览和转移智能体身份**。每个智能体的全局唯一标识由以下两部分组成：

* *agentRegistry*：以冒号分隔的字符串 `{namespace}:{chainId}:{identityRegistry}`，例如 `eip155:1:0x742...`。其中：
  * *namespace*：链家族标识符，EVM 链使用 `eip155`。
  * *chainId*：区块链网络标识符。
  * *identityRegistry*：ERC-721 注册表合约的部署地址。
* *agentId*：由注册表递增分配的 ERC-721 tokenId。

在本文中，ERC-721 的 *tokenId* 称为 *agentId*，*tokenURI* 称为 *agentURI*。ERC-721 代币的所有者就是智能体的所有者，可以转移所有权，也可以利用 `ERC721URIStorage` 的授权功能，将更新注册文件等管理工作交给操作员。

#### 智能体 URI 与智能体注册文件

*agentURI* 必须（MUST）解析为智能体注册文件。它可以（MAY）使用任意 URI 方案，例如 `ipfs://`（如 `ipfs://cid`）、`https://`（如 `https://example.com/agent3.json`），也可以使用经过 Base64 编码的 `data:` URI（如 `data:application/json;base64,eyJ0eXBlIjoi...`），将元数据完整存储在链上。注册文件 URI 发生变化时，可以通过 *setAgentURI()* 更新。

注册文件必须（MUST）采用以下结构：

```jsonc
{
  "type": "https://eips.ethereum.org/EIPS/eip-8004#registration-v1",
  "name": "myAgentName",
  "description": "智能体的自然语言描述，可以（MAY）包括其功能、工作方式、定价和交互方法",
  "image": "https://example.com/agentimage.png",
  "services": [
   {
      "name": "web",
      "endpoint": "https://web.agentxyz.com/"
    },
    {
      "name": "A2A",
      "endpoint": "https://agent.example/.well-known/agent-card.json",
      "version": "0.3.0"
    },
    {
      "name": "MCP",
      "endpoint": "https://mcp.agent.eth/",
      "version": "2025-06-18"
    },
    {
      "name": "OASF",
      "endpoint": "ipfs://{cid}",
      "version": "0.8", // https://github.com/agntcy/oasf/tree/v0.8.0
      "skills": [], // 可选（OPTIONAL）
      "domains": [] // 可选（OPTIONAL）
    },
    {
      "name": "ENS",
      "endpoint": "vitalik.eth",
      "version": "v1"
    },
    {
      "name": "DID",
      "endpoint": "did:method:foobar",
      "version": "v1"
    },
    {
      "name": "email",
      "endpoint": "mail@myagent.com"
    }
  ],
  "x402Support": false,
  "active": true,
  "registrations": [
    {
      "agentId": 22,
      "agentRegistry": "{namespace}:{chainId}:{identityRegistry}" // 例如 eip155:1:0x742...
    }
  ],
  "supportedTrust": [
    "reputation",
    "crypto-economic",
    "tee-attestation"
  ]
}
```

文件顶层的 *type*、*name*、*description* 和 *image* 字段应当（SHOULD）与 ERC-721 应用兼容。端点（*endpoints*）的数量和类型由开发者自行决定。端点中的 *version* 字段属于应当（SHOULD）提供的字段，而不是必须（MUST）提供的字段。

智能体可以（MAY）发布其端点，指向 A2A 智能体卡片、MCP 端点、智能体的 ENS 名称、DID，或智能体在任意链上的钱包，即使智能体未在该链注册也可以。

#### 端点域名验证（可选）

由于端点可能指向不受智能体所有者控制的域名，智能体可以（MAY）选择发布 `https://{endpoint-domain}/.well-known/agent-registration.json`，证明其控制某个 HTTPS 端点域名。该文件至少应包含 `registrations` 列表，也可以包含完整的智能体注册文件。如果该文件可以通过 HTTPS 访问，且其中某个 `registrations` 条目的 `agentRegistry` 和 `agentId` 与链上智能体相匹配，用户可以（MAY）将该端点域名视为已验证。如果端点域名与 `agentURI` 所引用的主要注册文件所在域名相同，则无需额外检查，因为该主要注册文件已经证明了域名控制权。

智能体应当（SHOULD）至少有一条注册记录，也可以有多条；注册记录中的所有字段均为必填。
*supportedTrust* 字段是可选（OPTIONAL）的。如果缺失或为空，则本 ERC 仅用于发现智能体，不用于建立信任。

#### 链上元数据

注册表通过增加 `getMetadata(uint256 agentId, string metadataKey)` 和 `setMetadata(uint256 agentId, string metadataKey, bytes metadataValue)` 函数扩展 ERC-721，以支持可选的额外链上智能体元数据：

```solidity
function getMetadata(uint256 agentId, string memory metadataKey) external view returns (bytes memory)
function setMetadata(uint256 agentId, string memory metadataKey, bytes memory metadataValue) external
```

设置元数据时，会发出以下事件：

```solidity
event MetadataSet(uint256 indexed agentId, string indexed indexedMetadataKey, string metadataKey, bytes metadataValue)
```

`agentWallet` 是保留键，不得通过 `setMetadata()` 或在 `register()` 期间设置，包括接受元数据数组的重载版本。它表示智能体的收款地址，初始值为所有者地址。要修改它，智能体所有者必须证明自己控制新钱包：对于 EOA，提供有效的 [EIP-712](https://eips.ethereum.org/EIPS/eip-712) 签名；对于智能合约钱包，使用 [ERC-1271](https://eips.ethereum.org/EIPS/eip-1271) 验证。调用方式如下：

```solidity
function setAgentWallet(uint256 agentId, address newWallet, uint256 deadline, bytes calldata signature) external
```

提供以下函数以读取和清除当前设置的钱包：

```solidity
function getAgentWallet(uint256 agentId) external view returns (address)
function unsetAgentWallet(uint256 agentId) external
```

转移智能体所有权时，`agentWallet` 会自动重置为零地址，新所有者需要重新验证收款钱包。

#### 注册

调用以下任一函数即可注册智能体，并铸造对应的身份代币：

```solidity
struct MetadataEntry {
string metadataKey;
bytes metadataValue;
}

function register(string agentURI, MetadataEntry[] calldata metadata) external returns (uint256 agentId)

function register(string agentURI) external returns (uint256 agentId)

// 之后通过 setAgentURI() 添加 agentURI
function register() external returns (uint256 agentId)
```

这会发出一个 Transfer 事件、一个针对保留键 `agentWallet` 的 MetadataSet 事件、每个额外元数据条目各自的 MetadataSet 事件（如有），以及：

```solidity
event Registered(uint256 indexed agentId, string agentURI, address indexed owner)
```

#### 更新 agentURI

可以调用以下函数更新 agentURI，并发出 URIUpdated 事件：

```solidity

function setAgentURI(uint256 agentId, string calldata newURI) external

event URIUpdated(uint256 indexed agentId, string newURI, address indexed updatedBy)

```

如果所有者希望将整个注册文件存储在链上，*agentURI* 应当（SHOULD）使用经过 Base64 编码的 data URI，而不是序列化后的 JSON 字符串：

```
data:application/json;base64,eyJ0eXBlIjoi...
```

### 信誉注册表

部署信誉注册表时，通过 `initialize(address identityRegistry_)` 设置 *identityRegistry* 地址，可通过以下函数查询：

```solidity
function getIdentityRegistry() external view returns (address identityRegistry)
```

*clientAddress* 对智能体提供的反馈包含一个有符号定点数值 *value*（`int128`）及其小数位数 *valueDecimals*（`uint8`，范围为 0–18），还可包含 *tag1* 和 *tag2*（由开发者自行定义，便于链上组合使用和筛选）、*endpoint* URI、指向含有额外信息的链下 JSON 文件的 URI，以及用于保证文件完整性的 KECCAK-256 哈希。建议使用 IPFS 或同类服务，便于使用子图或类似技术索引反馈。对于 IPFS URI，无需提供哈希。
除 *value* 和 *valueDecimals* 外，所有字段均为可选（OPTIONAL），因此链下文件也不是必需的，可以省略。

#### 提交反馈

任意 *clientAddress* 都可以通过调用以下函数添加新反馈：

```solidity
function giveFeedback(uint256 agentId, int128 value, uint8 valueDecimals, string calldata tag1, string calldata tag2, string calldata endpoint, string calldata feedbackURI, bytes32 feedbackHash) external
```

*agentId* 必须对应有效注册的智能体。*valueDecimals* 必须（MUST）在 0 到 18 之间。反馈提交者不得（MUST NOT）是该 *agentId* 的所有者或获授权操作员。*tag1*、*tag2*、*endpoint*、*feedbackURI* 和 *feedbackHash* 均为可选（OPTIONAL）。

如果提供 *feedbackHash*，它应是 *feedbackURI* 所引用内容的 KECCAK-256 哈希（`keccak256`），用于校验非内容寻址 URI 对应内容的完整性。对于 IPFS 或其他内容寻址 URI，*feedbackHash* 为可选（OPTIONAL），可以省略，例如设为 `bytes32(0)`。

调用成功后，发出以下事件：

```solidity
event NewFeedback(uint256 indexed agentId, address indexed clientAddress, uint64 feedbackIndex, int128 value, uint8 valueDecimals, string indexed indexedTag1, string tag1, string tag2, string endpoint, string feedbackURI, bytes32 feedbackHash)
```

反馈字段 *value*、*valueDecimals*、*tag1*、*tag2* 和 *isRevoked* 会与 feedbackIndex 一同存入合约存储。feedbackIndex 是 *clientAddress* 对 *agentId* 提交反馈时使用的、从 1 开始的计数器。*endpoint*、*feedbackURI* 和 *feedbackHash* 会通过事件发出，但不写入合约存储。其他智能合约可以读取这些信誉信号并用于自身业务。

如果提交反馈的客户本身也是智能体，应当（SHOULD）使用其链上可选元数据 `agentWallet` 指定的地址作为 clientAddress，方便聚合信誉。

| `starred` | 质量评分（0–100） | `87/100` | `87` | `0` |

| `ownerVerified` | 端点是否由智能体所有者控制（二元值） | `true` | `1` | `0` |

#### 撤销反馈

*clientAddress* 可以调用以下函数撤销反馈：

```solidity
function revokeFeedback(uint256 agentId, uint64 feedbackIndex) external
```

这会发出：

```solidity
event FeedbackRevoked(uint256 indexed agentId, address indexed clientAddress, uint64 indexed feedbackIndex)
```

#### 追加回应

任何人都可以调用以下函数追加回应。例如，*agentId* 对应的智能体可以补充退款信息，链下数据情报聚合服务也可以标记垃圾反馈：

```solidity
function appendResponse(uint256 agentId, address clientAddress, uint64 feedbackIndex, string calldata responseURI, bytes32 responseHash) external
```

其中，*responseHash* 是 *responseURI* 指向的文件内容的 KECCAK-256 哈希，用于保证完整性。对于 IPFS URI，无需提供此字段。

这会发出：

```solidity
event ResponseAppended(uint256 indexed agentId, address indexed clientAddress, uint64 feedbackIndex, address indexed responder, string responseURI, bytes32 responseHash)
```

### 验证注册表

**智能体通过该注册表请求验证工作结果，验证方智能合约则提交回应，供链上查询和追踪**。验证方可采用由质押机制保障的推理重新执行、zkML 验证器或 TEE 预言机等方式，接受或拒绝验证请求。

部署验证注册表时，通过 `initialize(address identityRegistry_)` 设置 *identityRegistry* 地址，并可按前文所述通过 `getIdentityRegistry()` 读取。

#### 验证请求

智能体通过以下函数请求验证：

```solidity
function validationRequest(address validatorAddress, uint256 agentId, string requestURI, bytes32 requestHash) external
```

该函数必须（MUST）由 *agentId* 的所有者或操作员调用。*requestURI* 指向链下数据，其中包含验证所需的全部信息，包括输入和输出。*requestHash* 是对该数据的承诺，即请求载荷的 `keccak256`，同时也是请求的标识。其他所有字段均为必填。

这会发出 ValidationRequest 事件：

```solidity
event ValidationRequest(address indexed validatorAddress, uint256 indexed agentId, string requestURI, bytes32 indexed requestHash)
```

#### 验证回应

验证方通过以下函数提交回应：

```solidity
function validationResponse(bytes32 requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag) external
```

只有 *requestHash* 和 *response* 为必填；*responseURI*、*responseHash* 和 *tag* 为可选。该函数必须（MUST）由原始请求指定的 *validatorAddress* 调用。*response* 是 0 到 100 之间的数值，可以作为二元结果使用（0 表示失败，100 表示通过），也可用中间值表示不同程度的验证结果。可选的 *responseURI* 指向链下验证证据或审计资料；如果该资源不在 IPFS 上，*responseHash* 用作其内容承诺；*tag* 则用于自定义分类或附加数据。

可以针对同一 *requestHash* 多次调用 validationResponse()，逐步更新验证结果，例如通过 *tag* 区分“软最终性”和“硬最终性”，或更新验证状态。

执行成功后，会发出包含全部函数参数的 *ValidationResponse* 事件：

```solidity
event ValidationResponse(address indexed validatorAddress, uint256 indexed agentId, bytes32 indexed requestHash, uint8 response, string responseURI, bytes32 responseHash, string tag)
```

合约存储 *requestHash*、*validatorAddress*、*agentId*、*response*、*responseHash*、*lastUpdate* 和 *tag*，供链上查询和其他合约使用。

#### 读取函数

```solidity
function getValidationStatus(bytes32 requestHash) external view returns (address validatorAddress, uint256 agentId, uint8 response, bytes32 responseHash, string tag, uint256 lastUpdate)

// 返回某个智能体的聚合验证统计。只有 agentId 是必填参数；validatorAddresses 和 tag 是可选筛选条件。
function getSummary(uint256 agentId, address[] calldata validatorAddresses, string tag) external view returns (uint64 count, uint8 averageResponse)
```

验证相关的激励和罚没由具体的验证协议管理，不在本注册表的范围内。

## 设计理由

* **智能体通信协议**：MCP 和 A2A 已广泛使用，今后也可能出现其他协议。本协议通过链上记录指向注册文件，允许随时添加端点，同时支持 MCP、A2A，以及钱包地址、DID、ENS 名称等信息。
* **反馈**：本协议沿用 A2A 已有的术语（如任务和技能）及 MCP 已有的术语（如工具和提示词），反馈信号的结构则保留充分的自定义空间。
* **Gas 代付**：由于客户不再需要注册，任何应用都可以利用 [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702) 简化用户提交反馈的流程。
* **索引**：反馈数据保存在链上，完整数据建议使用 IPFS，便于使用子图建立索引，供应用查询。
* **部署**：每类注册表预计在每条链上各部署一个实例。在链 A 注册并接收反馈的智能体，仍可在其他链上运行和交易。智能体也可以按需在多条链上注册。

## 安全注意事项

* 可能发生女巫攻击，虚增虚假智能体的信誉。本协议公开这些信号，并统一其数据格式。应用可以据此构建信誉系统，例如维护可信评价者名单，或为评价者建立信誉，再使用协议提供的筛选功能查询反馈。
* 链上指针和哈希无法删除，以保留完整的审计记录。
* 验证方的激励和罚没由具体的验证协议管理。
* 本 ERC 虽然能通过密码学确保注册文件与链上智能体相对应，但无法以此保证其宣称的能力确实可用，也无法保证其行为没有恶意。信誉、验证和 TEE 证明这三种信任模型用于帮助判断这些问题。
